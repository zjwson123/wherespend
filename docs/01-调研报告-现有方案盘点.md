# WhereSpend 调研报告：跨渠道账单混乱问题，别人是怎么解的

> 调研时间：2026-09
> 调研方式：GitHub / 开源社区 / 少数派 / 飞书社区 / App Store / 海外产品生态
> 调研目的：在动手设计之前，先回答两个问题——① 这个痛点有没有现成的成熟解法；② 如果自建，哪些技术路线已被验证可行。

---

## 0. 一句话结论

**痛点真实且普遍（连复式记账极客都深受其扰），但市面上没有一个"轻量 + 数据在自己手里 + 和日常工作流融合"的现成方案**。用户设想的"飞书机器人 + AI 分类 + 多维表格"路线，每一环都已被社区实践单独验证过，只是没有人把它们组装成一个开箱即用的产品——这正是这个项目的价值空间。

---

## 1. 痛点定义与行业验证

### 1.1 痛点的本质：渠道账单 ≠ 我的账本

支付宝、微信、京东白条、银行卡，每家都在用**渠道视角**记账：支付宝只知道"这笔走了我"，银行只知道"这笔扣了我的钱"。当支付宝绑定银行卡消费时，同一笔交易在两边各出现一次。这不是 bug，是渠道记账的天然属性。

**个人需要的却是消费视角**：一笔消费只记一次，"用哪个渠道付的"只是这笔消费的一个属性。

两种视角的错位，导致：
- 各渠道年度账单加起来 ≠ 实际总支出（重复计数）
- 转账、信用卡还款、余额宝划转混在"支出"里
- 没有任何单一渠道能看到全貌

### 1.2 行业验证：这是经典难题，不是个例

- GitHub 上 [double-entry-generator](https://github.com/deb-sig/double-entry-generator)（2k+ star，专门把支付宝/微信账单转复式记账的工具）的 [Issue #147「关于账单重复的处理方案？」](https://github.com/deb-sig/double-entry-generator/issues/147)：用户提出"微信里用京东小程序购物，京东账单和微信账单各生成一条记录"、支付宝与银行卡账单同样重复。维护者的回应是这是**不可避免的问题**，一般两种解法：记成多次（然后手动删）或规则去重。截至目前没有自动完美去重方案。
- 知乎长盛问题[《求快速记账软件，可以与微信、支付宝消费记录同步？》](https://www.zhihu.com/question/278100606)：结论是**国内监管下不存在官方聚合 API**，任何"自动同步"要么读通知、要么导账单文件、要么手动记。

**结论：不要指望"自动聚合各渠道账单"有一条免维护的完美路。** 可选路线只有三条：全量导入+去重（重）、通知流自动抓取（平台受限）、消费视角手动记（轻但依赖人）。

## 2. 四大流派盘点

### 流派 A：记账 App（手动 + 半自动增强）

| 产品 | 自动化能力 | 痛点覆盖 | 短板 |
|---|---|---|---|
| **钱迹**（600万+用户） | Android 无障碍读支付通知自动记账（需 Pro 会员）；iOS 受系统限制只能快捷指令/闪控球半自动；支持微信/支付宝账单文件导入 | 账单导入 + 识别去重较成熟 | iOS 自动记账受限；数据在厂商服务器；会员制 |
| **一木记账 / 滴水记账 / 小白记账** | 语音"午饭32"自动填金额/分类/账户 | 记录快 | 本质仍是独立记账 App，渠道重复问题要靠自觉只记一笔 |
| **咔皮记账** | 对话式 AI 记账，半年做到赛道 TOP1、百万用户（[智源社区访谈](https://hub.baai.ac.cn/view/47091)） | 验证了"聊天式记账"市场需求成立 | 闭源 SaaS，数据在厂商手里，无法自定义 |
| **荣耀 MagicOS 自动记账** | 系统级 AI 感知支付场景 | Android 厂商内最丝滑 | 绑定荣耀手机 |
| **今日记账 / 百事AA** | 账单导入去重 | — | 闭源、通用性一般 |

**评价**：这条流派证明了"语音/一句话记账"体验已经普及，但全部是**封闭 SaaS**——数据在别人服务器、分类规则不可控、和飞书工作流割裂。对一个有 DeepSeek API、有开发能力、日常泡在飞书里的用户，付费用别人的闭环不如自己搭。

### 流派 B：极客向复式记账（beancount 生态）

- [double-entry-generator](https://github.com/deb-sig/double-entry-generator)：支付宝/微信/招行账单 → beancount。复式记账在理论上是**唯一严谨正解**：支付宝绑卡消费记为 `支出:餐饮` 对 `资产:支付宝`，支付宝↔银行卡互转记为 Transfer 不计支出，天然无重复。
- 配套实践：[《关于使用 Beancount 记账我所知道的一切》](https://flyalready.com)、TripleZ 的月度导入工作流（按"最后导入日期"手动截断防重）。
- [Benature/bill](https://github.com/Benature/bill)：Python 脚本合并微信+支付宝官方 CSV，标记类型、去重、按月出图，号称"每月 10 分钟"。

**评价**：理论完美，工程门槛高——要导账单文件（微信账单还要等邮箱解压密码）、要维护账户映射 YAML、要看懂复式记账。**它解决的是"事后全量对账"，不是"随手记一笔"**。其中"转账不计入支出"的思想值得最小化移植，但整个体系不符合"轻量"要求。

### 流派 C：海外自托管 / SaaS

- **Maybe Finance**：曾爆火的自托管个人财务，已被收购并**停止服务**，大量用户外溢。
- **Actual Budget**（YNAB 式信封预算）/ **Firefly III**（复式记账）/ **ezBookkeeping**（国人开发的轻量自托管，自带移动端和 Telegram bot）：三者对比见 [ezBookChecking 官方对比页](https://ezbookkeeping.mayswind.net/zh-CN/comparison)。
- 海外产品的数据导入依赖**银行开放 API（Plaid 等）**，在国内完全不适用。

**评价**：需要一台常驻服务器 + Docker，面向海外银行生态。对"个人很方便使用"的要求来说太重，且同样没有解决国内渠道问题。ezBookChecking 的"自带 IM bot"形态值得借鉴。

### 流派 D：IM 机器人路线（与用户设想一致，重点调研）

#### D1. 海外：模式已充分成熟

- [n8n 模板：Telegram bot + GPT-4o OCR + 语音识别记账](https://n8n.io/workflows/11368-track-expenses-automatically-with-telegram-bot-using-gpt-4o-ocr-and-voice-recognition/)（评分 4.6）：发文字/语音/小票照片 → LLM 抽取 → 入库。
- [Auritrack](https://www.auritrack.com/telegram-expense-tracker)：商用 Telegram 记账 bot，支持对话记录、预算、问答、账单上传。
- GitHub 上大量个人项目（PayLog AI、gasti、SmartExpenseBot 等）实现了同一模式：**自然语言 → LLM 结构化抽取（金额/分类/商家/日期）→ 写 Google Sheets/数据库 → 回执**。

**模式验证充分，唯一问题是：它们都长在 Telegram/Discord 上，国内日常用不了。**

#### D2. 国内飞书生态：每个环节都有人单独跑通过

| 环节 | 已验证实践 |
|---|---|
| 快捷指令 → 多维表格记账 | 少数派[《iPhone快捷指令自动记账，懒人无痛记账神器》](https://sspai.com/post/86611)、[《借助iPhone快捷指令及飞书实现高效记账》](https://www.feishu.cn/content/7331276973480132611)（2秒记账，含表格+自动化流程+仪表盘完整搭建） |
| 短信自动化 → 飞书 webhook（通知流路线） | 少数派[《这才是真的自动记账，颠覆式记账完整教程》](https://sspai.com/post/87809)：监听银行/财付通扣款短信 → 正则取金额 → 发飞书机器人 → 写多维表格。局限：依赖短信、分类靠关键词映射、无 AI |
| 飞书机器人 + LLM + 多维表格（完整同款设想） | GitCode[《飞书记账助手开发全纪录：从零搭建一个智能记账机器人》](https://gitcode.csdn.net)（2026-06）：飞书开放平台**长连接**收消息 + 多维表格做存储 + 硅基流动 API + LangChain 做自然语言解析，与用户设想架构完全一致，证明可行；但它是个人博客教程，**没有沉淀为可复用的开源项目** |
| 多维表格做统计分析 | 飞书社区教程均搭配**仪表盘**（饼图/趋势图，手机端可用）+ 多视图筛选；多维表格还有官方 AI 字段/AI 捷径可做自动分类 |
| bot 生态成熟度 | 飞书开放平台支持 WebSocket **长连接模式（无需公网 IP、无需备案域名）**，个人免费注册团队即可创建自建应用；多维表格 API 完备（记录增删改查、字段管理），Go/Node/Python 官方 SDK 齐全 |

#### D3. 关键可行性问题的直接回答

> 用户疑问："仅靠飞书多维表格，能否随时随地筛选账单？"

**能，但有边界**：
- ✅ 移动端多维表格 App 支持：自定义视图（按月/按分类/按账户筛选，可保存多个预设视图）、仪表盘（图表随数据自动更新）、分组统计、快捷方式放桌面
- ✅ 配合 bot 问答（"这个月吃饭花了多少"）可以覆盖大部分"随手查"场景
- ⚠️ 边界：多维表格的仪表盘不如专业 BI 灵活，复杂交叉分析（如"近 6 个月各分类环比"）不如导出 CSV 后自己分析——但这属于低频深度需求，不影响日常使用

## 3. 方案对比总表

| 维度 | 记账 App（钱迹等） | beancount 脚本 | 海外自托管 | 飞书 bot 自建 |
|---|---|---|---|---|
| 记一笔的成本 | 低（语音/通知） | 高（导文件） | 高（手动/不适配国内） | **极低（一句话）** |
| 渠道重复解决 | 靠自觉/导入去重 | ✅ 理论严谨 | ❌ | ✅ 消费视角天然去重 |
| 数据归属 | 厂商 | ✅ 自己 | ✅ 自己 | ✅ 自己（多维表格随时导出） |
| 自定义分类/规则 | 有限 | ✅ 完全 | ✅ 完全 | ✅ 完全（prompt + 规则表） |
| 统计能力 | ✅ 成熟 | 依赖 fava/脚本 | ✅ | 多维表格仪表盘 + bot 问答，够用 |
| 部署/维护成本 | 零 | 中 | 高（服务器） | **低（单进程 + 长连接，本机/NAS/Serverless 均可）** |
| 与日常习惯融合 | 独立 App | 独立工作流 | 独立系统 | ✅ 就在每天开着的飞书里 |
| 隐私 | 数据出本机 | ✅ 本地 | ✅ 本地 | 消费文本过 DeepSeek API（可接受，敏感可脱敏） |

## 4. 调研最终结论

1. **不存在"自动聚合全部渠道账单"的合法免维护方案**（国内无开放 API，这是监管现实）。
2. 现成产品各有硬伤：记账 App 数据不在自己手里且 iOS 自动化受限；beancount 太重；海外自托管不适配国内且要养服务器。
3. **"IM 一句话 + AI 抽取 + 表格存储"的交互模式，在海内外都已被充分验证**（咔皮记账的百万用户、n8n 模板生态、飞书社区多篇教程），用户的方向判断是对的。
4. 缺的只是一次**组装**：把这些已验证的环节，围绕"消费视角记账"这个核心洞察，组装成一个轻量、可长期坚持的个人系统。这正是产品设计文档要做的事。
