# WhereSpend · 钱去哪了 —— 产品设计方案（PRD v1.0）

> 产品代号：WhereSpend（目录即名）
> 一句话：**在飞书里跟机器人说一句话，这笔消费就被记录、被分类、被统计了——永远只有一笔，永远不会重复。**

---

## 1. 为什么做：痛点的重新表述

用户原话的核心困扰：*"支付宝走银行卡付一笔钱，支付宝账单记一次，银行卡账单又记一次，月度年度汇总永远算不清真实花了多少。"*

拆开看，这其实是三层问题：

| 层 | 问题 | 根因 |
|---|---|---|
| 记录层 | 各渠道账单交叉重复 | 渠道以自己视角记账，一笔交易天然出现在多条流水里 |
| 归属层 | 不知道"总支出"到底是多少 | 把"资金流"和"消费"混为一谈：转账、还款也被算成"花" |
| 消费层 | 不知道钱花在了哪 | 各渠道分类体系互不相通，无法合并分析 |

**核心洞察：解药不是"更好地聚合渠道账单"，而是换一个记账主体——不记"渠道的流水"，只记"我的消费"。**

一笔消费从发生那一刻起就只有一个主体：我买了什么、花了多少。至于从支付宝出还是从银行卡出，只是这笔消费的**属性**，不该成为账本的**骨架**。这样：
- 重复问题**天然消失**（一笔消费只记一次，不存在两份账单）
- "真实总支出"天然正确（转账/还款记为"转账"类型，不进消费统计）
- 渠道信息不丢失（作为字段保留，想看"这个月微信付了多少"随时可筛）

## 2. 产品定位

- **给谁**：首先给自己（单用户起手），架构上预留家庭共记。
- **是什么**：一个长在飞书里的 AI 记账助手 + 一张多维表格账本 + 一组自动化统计。不是一个 App，不装新东西。
- **不是什么**：不做预算管理大师、不做理财、不做发票报销、不追求 100% 记全每一笔。
- **成功标准**（个人产品的成功定义）：
  1. **坚持率**：连续 3 个月，每月记账 ≥ 60 笔（覆盖主要消费）
  2. **信任度**：月底自己算的总支出与各渠道账单交叉核对误差 ≤ 5%（漏记小额可接受，大额不漏）
  3. **成本**：每月总成本 ≤ 5 元（DeepSeek API）+ 0 元运维时间

## 3. 产品原则（所有功能设计的裁判）

1. **一笔消费只记一次** —— 账本骨架是"消费"，渠道只是属性。这是产品存在的理由。
2. **5 秒法则** —— 从想记到记完（发出消息→收到回执）不超过 5 秒、不超过 1 次输入。任何让记录变慢的功能都可以砍。
3. **允许不完美** —— 漏记不焦虑：小于 20 元的漏记无所谓，月度对账兜底找回大额。不为"记全"牺牲"轻"。
4. **数据主权** —— 数据 100% 在自己的多维表格里，随时一键导出 CSV，AI 只是加工者不是持有者。
5. **渐进复杂度** —— MVP 只有"说一句话"一个交互；查询、对账、周报都是后置的可选能力，永远不强制。

## 4. 核心用户旅程

### 4.1 记一笔（主路径，每天 N 次）

```
用户（在飞书私聊 bot）：「午饭 35」
                     或「昨天打车去机场 87，微信付的」
                     或直接发一条语音说上面这些话
bot（2 秒内回复卡片）：
  ✅ 已记录
  餐饮 · 午饭                ¥35.00
  2026-09-21 12:30 · 支付宝
  [分类不对？点此修改]
多维表格：新增一行，仪表盘数字即时刷新
```

规则细节：
- **不说的字段不猜死**：没说账户就默认上次的账户（或"未指定"），没说日期就默认现在。**唯一必须有的是金额**，金额缺失时 bot 追问一次（也只追问这一个字段）。
- **一句话多笔**支持：「午饭35 打车12」拆成两笔（M1 再做，MVP 可先不做）。
- **自然语言边界**："大概三十多"→ 追问确认还是取 30？→ 追问一次，宁可多一句也不记错钱。
- **收入、转账同样支持**：「发工资 25000」「支付宝转银行卡 3000」→ 类型自动识别为收入/转账，转账不进消费统计。
- **修改**：回执卡片点「修改」弹出表单（金额/分类/账户/备注），或直接回复 bot「刚才那笔改成 40」。

### 4.2 查一下（次路径，每周 N 次）

```
用户：「这个月花了多少」
bot：本月总支出 ¥4,286
     Top3：餐饮 ¥1,820 / 购物 ¥950 / 交通 ¥520
     较上月同期 +12%

用户：「上周外卖花了多少」
bot：上周「餐饮·外卖」共 6 笔，合计 ¥284
```

查询走同一条链路：DeepSeek 把问题转成对多维表格的查询（时间范围 + 筛选条件 + 聚合方式），结果用一句话 + 简短结构回给用户。**能一句话答的不发长报告。**

### 4.3 看全局（低频，每月 1-2 次）

打开多维表格：
- **仪表盘**：本月支出总额、分类占比饼图、近 30 天日消费趋势、账户分布
- **预设视图**：按月视图 / 按分类视图 / 按账户视图 / 大额消费（≥500）视图——每个都是配好筛选条件的一次点击

### 4.4 月度对账（兜底，每月 1 次，可选）

```
用户：（把支付宝/微信导出的账单 CSV 发给 bot）「对一下 8 月的账」
bot：8 月支付宝账单共 87 笔。
     ✅ 66 笔已匹配到你记的账（时间±10min 且金额一致）
     ⚠️ 15 笔疑似漏记（多为 <50 元），其中 3 笔 ≥100：
        09-12 盒马 ¥216 / 09-18 加油 ¥400 / ...
        [一键补记]（逐笔确认后写入）
     💡 6 笔是转账/还款，已自动忽略
```

这是整个产品的**信任基石**：手动记账必然漏，与其假装不漏，不如每月 10 分钟把官方账单和自己的账本对一次——既补漏，又持续校准"我的账本 ≈ 真实消费"的可信度。去重逻辑很朴素：同一时间窗内金额相同的渠道流水只对应一条消费记录。

## 5. 数据模型

### 5.1 多维表格主表「账本」字段设计

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| 日期 | 日期时间 | ✅ | 默认记录时刻，支持"昨天/上周五"解析 |
| 类型 | 单选 | ✅ | 支出 / 收入 / 转账 / 还款（**转账/还款不进消费统计**——复式记账思想的最小化移植） |
| 金额 | 货币 | ✅ | 单位元，保留 2 位 |
| 事项 | 文本 | ✅ | 原始描述清洗后的短语，如「午饭」「打车去机场」 |
| 分类 | 单选 | ✅ | 一级分类，见 5.2 |
| 子分类 | 单选 | 可选 | 如 餐饮→外卖/堂食/咖啡 |
| 支付账户 | 单选 | 可选 | 支付宝 / 微信 / 招行卡 / 京东白条 / 现金 / …（**属性，不是账本维度**） |
| 来源平台 | 单选 | 可选 | 记录消费发生地：京东 / 美团 / 淘宝 / 线下 / …（与支付账户区分：在美团下单用支付宝付，平台=美团、账户=支付宝） |
| 备注 | 文本 | 可选 | |
| 原始语句 | 文本 | 自动 | 用户对 bot 说的原话，留作审计与 AI 再训练 |
| 记录来源 | 单选 | 自动 | bot 记录 / 对账补记 / 手动表格 |
| 消费对象 | 文本 | 可选 | 给谁花的（自己/家庭/某成员），为家庭共记预留 |

### 5.2 分类体系（一级 10 类，克制）

餐饮 / 购物 / 居家 / 交通 / 娱乐 / 医疗 / 人情往来 / 学习 / 宠物 / 其他

- 宁少勿多：分类的意义是回答"钱去哪了"，10 类已足够；先粗后细，某类连续 3 个月占比 >30% 再考虑拆子分类。
- 分类规则对用户**可教**：回复 bot「以后星巴克都算餐饮-咖啡」，规则落表（见 7.3 规则表），AI 下次优先套用。

## 6. 交互与体验细节

### 6.1 对话语法（用户需要记住的全部）

只有一条：**「干了什么 + 多少钱」，其他全都可选。」

| 你说 | bot 理解为 |
|---|---|
| 午饭 35 | 餐饮 / 35 / 今天 / 默认账户 |
| 昨天打车去机场 87 微信 | 交通 / 87 / 昨天 / 微信 |
| 发工资 25000 | 收入 / 25000 |
| 支付宝转银行卡 3000 | 转账（不计支出）/ 3000 |
| 星巴克 | ⚠️ 没有金额 → 追问「花了多少？」（唯一会追问的字段） |

### 6.2 回执卡片

- 结构化确认（分类/金额/账户一眼可校对）+ 一个「修改」按钮 + 修改后原卡片原地更新。
- 回执即凭证：飞书消息记录天然成为消费流水的时间线，和表格互为备份。

### 6.3 语音

飞书语音消息 bot 可收到音频文件。M1 接入语音转文字（飞书 ASR 或 whisper），实现"按住说一句"零打字记账——这是移动端体验的关键补全。

### 6.4 防呆

- 同一分钟内相同金额的重复消息 → bot 提示「刚记过一笔 35，是重复了吗？」
- 金额异常大（如 >5000）→ 回执里加一行「金额较大，请确认」。

## 7. 技术架构（刻意从简）

### 7.1 架构图

```
飞书用户 ⇄ 飞书开放平台（自建应用·机器人，WebSocket 长连接，无需公网 IP）
                  │ 消息事件
                  ▼
        WhereSpend 服务（单进程，Node.js/Python）
          ├─ 意图识别：记账 or 查询 or 修改 or 对账
          ├─ DeepSeek API（chat completions，JSON 输出）
          │     ├─ 抽取：{金额, 事项, 类型, 日期, 账户, 分类}
          │     └─ 查询：自然语言 → 结构化查询条件
          ├─ 规则表（本地）：用户教的分类规则，优先于 AI 猜测
          ├─ 飞书多维表格 API：写入/查询/更新记录（官方 SDK）
          └─ 回执：飞书消息卡片（interactive card）
```

### 7.2 部署（零成本或近零成本）

- **最小**：一台常开的 Mac/NAS 上 `pm2` 跑一个进程（长连接模式不需要公网 IP、域名、备案）。
- **进阶**：任意 1 核 1G 云主机 / 免费层 Serverless。
- 成本：飞书个人版免费；DeepSeek API 按当前价格，个人月均百次调用约几毛到几元。

### 7.3 AI 工程要点（决定体验成败的部分）

1. **结构化输出而非自由文本**：DeepSeek 以 JSON Schema 约束输出（`{"amount":35,"item":"午饭","type":"expense","category":"餐饮","date":"2026-09-21","account":null}`），解析失败重试一次，仍失败则走规则兜底（正则抽数字 + 关键词分类表）。
2. **分类 prompt 内置上下文**：分类清单 + 每类 5 个示例 + 用户规则表内容，每次请求带上（token 极少，成本忽略不计）。
3. **规则优先级**：用户显式教的规则 > AI 判断 > 关键词表。让"教它"比"改它"更顺手，系统会越用越准。
4. **隐私**：只把单句消费描述发给 DeepSeek，不发送姓名、卡号等；表格中的全量数据永不出飞书。
5. **延迟**：记账链路必须 <3s（只调一次 LLM + 一次表格写入）；查询链路可放宽到 5s。

### 7.4 多维表格侧配置

- 主表 1 张（见 §5.1）+ 仪表盘 1 个 + 预设视图 4 个（本月/分类透视/账户分布/大额）。
- 进阶：多维表格自带自动化，可配"每月 1 号 bot 推送上月月报卡片"。

## 8. 迭代路线

| 阶段 | 周期 | 范围 | 验收 |
|---|---|---|---|
| **M0 能记** | 1 个晚上 | 建表 + 机器人收消息 + DeepSeek 抽取 + 写表 + 文本回执 | 「午饭 35」→ 表格里出现正确一行 |
| **M1 好用** | 1 周 | 回执卡片可修改、查询问答、语音、规则学习（"以后X算Y"）、重复检测、仪表盘与预设视图 | 自己连续 7 天只靠 bot 记账 |
| **M2 可信** | 1 个月 | 月度账单 CSV 对账补漏、月报推送、预算软提醒（分类超阈值提醒一次，不唠叨） | 月度对账后误差 ≤5%，坚持 3 个月 |
| **M3 可扩**（可选） | — | 家庭共记（消费对象字段启用）、iOS 快捷指令入口（锁屏一句话直达 bot）、小票图片识别 | — |

## 9. 风险与对策

| 风险 | 判断 | 对策 |
|---|---|---|
| 漏记导致放弃 | 最大真实风险 | 原则 3「允许不完美」+ M2 对账兜底；产品话术上明确"记 70% 的消费已足够回答'钱去哪了'" |
| AI 分类不准 | 中 | 卡片一键改 + 规则学习，准确率随使用上升；分类只有 10 类，本身降低出错面 |
| 每次都要切到飞书找 bot，入口还是有点深 | 中 | 飞书支持把 bot 会话置顶/加桌面快捷方式；M3 增加快捷指令入口（锁屏/敲背面触发，预填消息发给 bot） |
| DeepSeek 服务波动 | 低 | 规则兜底链路（正则+关键词表）保证"能记上"，事后补分类 |
| 飞书依赖 | 低 | 数据主权原则：表格随时导出 CSV；服务代码开源在本仓库，迁移成本一天 |
| 长连接进程挂了没人知道 | 低 | pm2 守护 + 每日心跳消息（bot 每天给自己发一条存活确认，M1 加） |

## 10. 与"用现成 App"的最终对账（为什么值得自建）

- 钱迹/咔皮等解决的是"记"的效率，但数据、规则、统计口径都在厂商手里，且无法和飞书工作流融合；
- 本方案 = 已被验证的交互模式（§调研 D1/D2） + 自己的数据主权 + 自己的分类规则 + 近零成本，工程量约等于 M0 一个晚上 + M1 一周的个人项目。
- **这不是重新发明轮子，而是把四个已经各自跑通的轮子（飞书长连接 bot、DeepSeek 结构化抽取、多维表格存储与仪表盘、月度账单对账）装在同一辆很小的车上。**
